# Reflexion personal: Redis y JWT en los microservicios

Al trabajar en este proyecto entendí que Redis y JWT resuelven problemas distintos, aunque pueden complementarse. Redis permite reutilizar datos temporales y reducir consultas repetidas a PostgreSQL; JWT permite que los servicios comprueben la identidad y los permisos de quien solicita una operacion. No considero que deban agregarse a todos los endpoints por defecto: su uso debe responder a una necesidad concreta y respetar la naturaleza de los datos.

## Por que usar Redis

El catalogo de libros es una buena candidata para la cache porque varias personas pueden consultar los mismos datos y, normalmente, hay mas lecturas que cambios. Si cada consulta vuelve a PostgreSQL, se repite trabajo que ya se hizo. Redis puede guardar por un periodo breve la respuesta de una lectura frecuente, reducir esa carga y responder con menor latencia. En este proyecto ya existe un patron cache-aside en el servicio SOAP: `GET /books` y `GET /books/<isbn>` buscan primero en Redis, consultan el repositorio cuando no encuentran la clave y guardan el resultado con un TTL de 180 segundos.

Tambien veo usos posibles en `GET /books/minimal` y en la consulta de conceptos si las mediciones muestran que se repiten mucho. En cambio, no cachearia indiscriminadamente registros, pagos, sesiones ni respuestas personalizadas. La informacion de autenticacion y los datos privados requieren controles distintos; guardar un JWT completo o contrasenas en Redis no es una solucion adecuada.

## Endpoints donde aplicaria cada mecanismo

- **Redis:** lecturas publicas y repetidas del catalogo, principalmente `GET /books` y `GET /books/<isbn>`. Como siguiente paso evaluaria `GET /books/minimal` y `GET /books/concepts`. Usaria claves con un espacio de nombres, por ejemplo `project_bien:books:all` y `project_bien:books:<isbn>`, y un TTL acorde con la frecuencia de cambios.
- **JWT:** `GET /users`, `POST /users`, las rutas de pedidos (`GET/POST /orders`, `GET /orders/<id>` y `PATCH /orders/<id>`), las rutas de pagos (`GET/POST /payments`), la escritura de autores (`POST /authors`) y las operaciones de escritura del catalogo SOAP (`POST`, `PUT`, `PATCH` y `DELETE /books`). Cada ruta debe pedir solo los roles que realmente necesita. En el catalogo SOAP, el guard actual valida la firma y expiracion del JWT, pero no el rol; yo agregaria tambien esa comprobacion a las operaciones administrativas. Las lecturas publicas de autores y libros no necesitan JWT si la politica del producto es mantenerlas publicas.

## Como lo implementaria

Para Redis mantendria un cliente compartido por proceso, configurado mediante `REDIS_URL`, como el que ya existe en `apps/services/redis_cache.py`. En un endpoint de lectura usaria el patron cache-aside: consultar la clave, leer PostgreSQL si no existe, serializar el resultado y guardarlo con expiracion. Despues de que una escritura se confirme correctamente, invalidaria tanto la clave del libro afectado como la clave de la lista, por ejemplo `books:<isbn>` y `books:all`. La invalidacion debe ocurrir despues de persistir el cambio, y probaria por separado los caminos de creacion, actualizacion y eliminacion para evitar entregar datos antiguos. Actualmente el servicio tiene la lectura cacheada, pero esa invalidacion posterior a cambios es una mejora pendiente. Ademas, antes de considerar completa la invalidacion de eliminaciones, corregiria `DELETE /books/<isbn>`: ahora valida que el libro exista, pero no lo elimina del repositorio.

La cache debe poder fallar sin detener una lectura no sensible: si Redis no esta disponible, el servicio puede consultar PostgreSQL directamente. El cliente actual ya se comporta de forma opcional cuando Redis no responde. Para datos personales, pagos y autorizacion no aplicaria esta tolerancia de manera que una falla conceda acceso; una falla de Redis nunca debe significar que una solicitud queda autenticada.

Para JWT compartiria `JWT_SECRET_KEY` entre los servicios que validan los tokens, la protegeria como secreto de entorno y no la incluiria en el codigo. Cada servicio verificaria la firma HS256, la expiracion y los claims necesarios antes de ejecutar la operacion. Tambien validaria el rol en el mismo limite de la ruta, no solo la existencia de un token. Mantendria los tokens con duracion limitada. Si el proyecto necesita revocarlos antes de que expiren, podria anadir un identificador `jti` y guardar en Redis una marca de revocacion con TTL hasta la expiracion; no guardaria el JWT completo ni usaria Redis como sustituto de verificar su firma.

## Conclusion

Mi conclusion es que Redis aporta valor cuando evita trabajo repetido en lecturas de alto uso, y JWT cuando una operacion requiere identidad o permisos. Para este proyecto empezaria ampliando con cuidado la cache del catalogo y agregando invalidacion despues de las escrituras, mientras mantengo JWT en las rutas privadas y de modificacion. Mediria el uso y probaria tambien los casos de cache vacia, datos actualizados, token vencido y falta de Redis. Asi cada tecnologia resuelve un problema concreto sin convertir la arquitectura en algo mas complejo de lo necesario.
